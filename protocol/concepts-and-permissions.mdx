---
title: "Concepts and Permissions"
---

The Swig program is role-based. The main mental model is:

- one Swig config account
- one wallet-address PDA used during execution
- one or more roles
- each role binds a `role_id`, one authority, and one or more actions

If you are trying to understand why a wallet operation succeeds or fails, these
are the concepts that matter.

## Swig account vs wallet address

The config account stores protocol state:

- the wallet ID
- the account bump
- the wallet-address bump
- the current role count
- the role counter used to assign new `role_id` values

The wallet-address PDA is the address used in execution flows. Higher-level
SDKs usually hand you both the config address and the wallet address because
the program needs both pieces.

## Roles and `role_id`

A role is the core authorization unit.

Each role stores:

- a stable `role_id`
- one authority type and its authority payload
- one or more typed actions

`role_id` matters because execution and recovery do not identify a signer only
by public key. They authenticate a specific role and then evaluate that role's
actions.

## Authority types

The current on-chain authority enum supports:

- `Ed25519`
- `Ed25519Session`
- `Secp256k1`
- `Secp256k1Session`
- `Secp256r1`
- `Secp256r1Session`
- `ProgramExec`
- `ProgramExecSession`

Session authorities are temporary forms of the base authority types. They carry
session-specific state and are authenticated through the session path rather
than the standard path.

## Permission families

Actions are typed permission records attached to roles.

| Family | Permissions | What they control |
|------|-------------|-------------------|
| Broad access | `All`, `AllButManageAuthority`, `ManageAuthority` | root-like access, broad execution, and authority management |
| SOL limits | `SolLimit`, `SolRecurringLimit`, destination variants | lamport spending ceilings |
| Token limits | `TokenLimit`, `TokenRecurringLimit`, destination variants | SPL token spending ceilings |
| Program access | `Program`, `ProgramAll`, `ProgramCurated`, `ProgramScope` | CPI access from the wallet |
| Staking | `StakeLimit`, `StakeRecurringLimit`, `StakeAll` | stake-related execution |
| Sub-accounts | `SubAccount` | sub-account creation and use |
| Lifecycle and recovery | `CloseSwigAuthority`, `RecoveryAuthority` | closing wallets and constrained recovery |

## Common role patterns

Most integrations reason about a few recurring role shapes:

- a root or admin role with broad authority-management access
- an execution role with spend and program permissions
- an optional recovery role with `RecoveryAuthority`
- optional session roles for shorter-lived delegated access

## Important permission distinctions

Some permissions are easy to confuse:

- `All` is the broadest role marker.
- `AllButManageAuthority` still allows broad execution, but excludes authority
  and sub-account management.
- `ManageAuthority` is for adding, removing, and updating authorities.
- `RecoveryAuthority` is intentionally narrower than `ManageAuthority`. It only
  grants access to the dedicated recovery path.
- `ProgramAll` grants unrestricted CPI access and should be treated as highly
  privileged.
- `ProgramScope` is the most specialized program permission. It binds a program,
  target account, and numeric field layout so the program can enforce scoped
  limits.

## How higher-level SDKs map onto this

Higher-level SDKs often hide the storage details, but they still rely on this
same model:

- a wallet operation eventually names a role
- that role authenticates one authority
- the role's actions decide whether the operation is allowed
