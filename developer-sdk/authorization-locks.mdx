## Introduction

An authorization lock reserves an asset amount for a role until it is spent,
released, or expires. Use it when an authorized operation needs a temporary hold
on SOL or tokens while other roles continue using the wallet.

The backend prepares unsigned transactions. Your application handles approval,
signing, and submission. Hosted support remains under review in
[TypeScript/Python PR #66](https://github.com/anagrambuild/swig-developer-sdk/pull/66)
and [Rust PR #79](https://github.com/anagrambuild/swig-developer-sdk/pull/79), and
requires matching backend routes and the authorization-lock program.

## Input

| Operation | Parameter | Description |
| :--- | :--- | :--- |
| All | Wallet config and network | Existing wallet on the configured client |
| Read | `includeExpired` / `include_expired` | Include expired and fully captured records |
| Add/remove | Requester and fee payer | Authority for the operation and public fee-payer key |
| Add | `amount` | Lamports or token base units; use an exact integer value |
| Add | `mint` | Omit for SOL; supply a mint to hold tokens in the wallet's associated token account |
| Add | `durationSlots` / `duration_slots` or `expirySlot` / `expiry_slot` | Choose exactly one; the role's maximum duration still applies |
| Remove | `lockId` / `lock_id` | ID of the hold to release or prune |

The acting role needs `ManageAuthorizationLocks { max_duration_slots }`, even
with `All`, and a limited role also needs the asset's spending permission.
Grant this through the [Protocol SDK](/protocol/authorization-locks); the hosted
add-role API does not expose it. A delegated role cannot raise its own duration bound.

Only the holder can release an active hold. The holder or an eligible managing
role can prune expired or fully captured records. Normal spending by the holder
captures the hold and reduces its remaining amount; zero is valid.

## Output

| Read field | Meaning |
| :--- | :--- |
| `currentSlot` / `current_slot` | Slot used to evaluate the returned holds |
| `nextLockId` / `next_lock_id` | Next lock identifier |
| `locks[].lockId` / `lock_id` | Hold identifier |
| `locks[].roleId` / `role_id` | Holder role |
| `locks[].assetAccount` / `asset_account` | Account containing the reserved asset |
| `locks[].mint` | Token mint; absent for native SOL |
| `locks[].amount` | Remaining base-unit amount as an exact decimal string |
| `locks[].expirySlot` / `expiry_slot` | Expiry slot as an exact decimal string |
| `locks[].active` | True while unexpired with a nonzero remaining amount |

## SDK example

These examples target the SDK changes linked above. Use server-side clients
from [Client setup](/developer-sdk/integration-paths). Preparation alone does
not create or remove a hold; sign, submit, confirm, then query again.

<Tabs>
<Tab title="TypeScript">

This function uses an existing server-side `SwigClient` and public addresses.
The returned transaction is prepared, not submitted.

```typescript
import { SwigClient } from '@swig-wallet/developer-sdk';

async function prepareHold(
  swig: SwigClient,
  configAddress: string,
  requesterPublicKey: string,
  feePayer: string,
) {
  const wallet = swig.wallets.use(configAddress, {
    requesterAuthority: { ed25519: { publicKey: requesterPublicKey } },
  });
  const prepared = await wallet.addAuthorizationLock({
    feePayer,
    amount: '1000000',
    durationSlots: 150,
  });
  const holds = await wallet.getAuthorizationLocks({ includeExpired: true });
  return { prepared, holds };
}
```

Use `wallet.removeAuthorizationLock({ feePayer, lockId })` to prepare release
of an existing hold. Use decimal strings or `bigint` for amounts beyond
JavaScript's safe integer range. Prepared lock kinds are
`add-authorization-lock` and `remove-authorization-lock` (wire values 10 and 11).

</Tab>
<Tab title="Python">

```python
from swig_developer_sdk import AuthorizationLocksResult, PreparedTransaction, SwigClient

async def prepare_hold(
    swig: SwigClient,
    config_address: str,
    requester_public_key: str,
    fee_payer: str,
) -> tuple[PreparedTransaction, AuthorizationLocksResult]:
    wallet = swig.wallets.use(
        config_address,
        requester_authority={"ed25519": {"public_key": requester_public_key}},
    )
    prepared = await wallet.add_authorization_lock(
        fee_payer=fee_payer,
        amount=1_000_000,
        duration_slots=150,
    )
    holds = await wallet.get_authorization_locks(include_expired=True)
    return prepared, holds
```

Use `wallet.remove_authorization_lock(fee_payer=fee_payer, lock_id=lock_id)`
to prepare release. The SDK validates amounts and expiry values as unsigned
64-bit integers and lock IDs as unsigned 32-bit integers.

</Tab>
<Tab title="Rust">

```rust
use solana_pubkey::Pubkey;
use swig_developer_sdk::{
    AuthorizationLockError, AuthorizationLockExpiry,
    PrepareAddAuthorizationLockArgs, PrepareRemoveAuthorizationLockArgs,
    PreparedTransaction, WalletAuthority, WalletClient,
};

async fn prepare_hold(
    client: &WalletClient,
    swig_config_address: Pubkey,
    fee_payer: Pubkey,
    requester_authority: WalletAuthority,
) -> Result<PreparedTransaction, AuthorizationLockError> {
    client.prepare_add_authorization_lock(PrepareAddAuthorizationLockArgs {
        swig_config_address,
        fee_payer,
        requester_authority,
        mint: None,
        amount: 1_000_000,
        expiry: AuthorizationLockExpiry::DurationSlots(150),
    }).await
}

async fn prepare_release(
    client: &WalletClient,
    swig_config_address: Pubkey,
    fee_payer: Pubkey,
    requester_authority: WalletAuthority,
    lock_id: u32,
) -> Result<PreparedTransaction, AuthorizationLockError> {
    client.prepare_remove_authorization_lock(PrepareRemoveAuthorizationLockArgs {
        swig_config_address, fee_payer, requester_authority, lock_id,
    }).await
}
```

Read with `client.get_authorization_locks(&swig_config_address, true).await?`.
The boolean includes expired and fully captured records. Rust returns typed
`u64` amounts and slots, `u32` IDs, and `Pubkey` addresses.

`AuthorizationLockExpiry::ExpirySlot(slot)` chooses an absolute expiry instead.
The native secp256k1 and raw secp256r1 transaction signers handle both lock
instructions. ParticipantSet requesters use the existing approval compilation
flow before signing the compiled transaction.
