Guardian recovery is an add-on flow around wallet creation. It is not part of a
plain no-policy wallet create.

## The important model

Recovery in this SDK is policy-backed:

- create the wallet from a recovery-enabled policy
- let `swig.wallets.create(...)` return a `recoverySetup` plan
- submit wallet creation
- call `wallet.recovery.prepareSetup(...)`
- submit the recovery setup transactions in order
- later use `start`, `cancel`, and `execute` for the live recovery lifecycle

If the policy is not recovery-enabled, you should treat the result as a normal
wallet create flow and expect `recoverySetup` to be absent.

## Create from a recovery-enabled policy

```typescript
const created = await swig.wallets.create({
  feePayer,
  policyId,
  initialUser: {
    secp256r1: {
      publicKey: passkeyPublicKey,
    },
  },
  recovery: {
    guardianPubkey: guardianPublicKey,
    delaySeconds: 86_400,
  },
});
```

The `recovery` object is used to help build the returned setup plan. Recovery
is still completed as a follow-up flow. Wallet creation itself does not finish
recovery setup.

## What `create(...)` gives you

For a recovery-enabled create flow, the returned categories matter:

- `creationTransaction` creates the wallet
- `clientAuthorityTransactions` are the transactions the current wallet
  authority must sign
- `operatorSignedTransactions` are already signed by the backend recovery
  operator
- `recoverySetup` is the plan you feed into `prepareSetup(...)`

## Recovery setup

After wallet creation is submitted, prepare the follow-up recovery setup:

```typescript
const wallet = swig.wallets.use(created.wallet);

const setup = await wallet.recovery.prepareSetup({
  feePayer,
  ...created.recoverySetup!,
});
```

That returns two main prepared transactions:

- `addAuthorityTransaction`
- `configureRecoveryTransaction`

## Who signs what

The setup path is intentionally split:

| Transaction | Who signs |
|-------------|-----------|
| `creationTransaction` | fee payer or sponsor path |
| `addAuthorityTransaction` | current wallet authority |
| `configureRecoveryTransaction` | backend recovery operator already signs it |

Do not authority-sign `operatorSignedTransactions` again.

## Ongoing recovery lifecycle

After setup:

- the guardian starts recovery with `wallet.recovery.start(...)`
- the current wallet authority can cancel with `wallet.recovery.cancel(...)`
- the guardian executes with `wallet.recovery.execute(...)` after the delay

```typescript
const start = await wallet.recovery.start({
  feePayer,
  guardianPubkey: guardianPublicKey,
  newAuthority: newAuthorityPublicKey,
});

const cancel = await wallet.recovery.cancel({
  feePayer,
});

const execute = await wallet.recovery.execute({
  feePayer,
  newAuthority: newAuthorityPublicKey,
});
```

The guardian signs `start` and `execute`. The current wallet authority signs
`cancel`.

## Policy metadata and `targetRoleId`

The SDK also reads policy metadata through `swig.wallets.getPolicy(policyId)`.
That is where it finds fields such as:

- `guardianEnabled`
- `guardianAuthority`
- `guardianDelaySeconds`

Most apps should let `created.recoverySetup` be the source of truth for the
follow-up setup flow.

`targetRoleId` is an advanced option. Most integrations omit it and recover the
main user role. Only set it when you are intentionally binding recovery to a
specific non-default role.
