## Introduction

Signing proves that an authorized wallet member approves a prepared operation.
Use this step after preparation and before submission. Your application owns
user approval, signer selection, and key custody; the hosted API key stays on
your server.

TypeScript's `/signers` entrypoint and Python's helpers use application callbacks.
Rust's native signers hold local keys through `Arc`. These helpers make no hosted
API calls. Inspect transaction intent, permissions, and freshness before signing.

## SDK examples

### Ed25519 and application-defined signers

TypeScript/Python callbacks receive the base64 transaction and prepared record,
and return signed base64. Rust adds a signature to the correct native slot.
Use `prepared.transaction` after resolving participant and embedded signatures.
Repeat for each required application-owned Ed25519 signer.

<CodeGroup>

```typescript TypeScript
import {
  signPreparedTransaction,
  type PreparedTransaction,
} from '@swig-wallet/developer-sdk/signers';

declare const prepared: PreparedTransaction;

const signed = await signPreparedTransaction(prepared, {
  signTransaction: async (transaction) => {
    return applicationSigner.signSerializedTransaction(transaction);
  },
});
```

```python Python
from swig_developer_sdk import sign_prepared_transaction

async def sign_with_application(transaction, _prepared):
    return await application_signer(transaction)

signed = await sign_prepared_transaction(
    prepared,
    sign_transaction=sign_with_application,
)
```

```rust Rust
use std::io;

use solana_signer::Signer;

let mut signed_transaction = transaction;
signed_transaction.sanitize()?;
let required = usize::from(signed_transaction.message.header().num_required_signatures);
let signer_index = signed_transaction
    .message
    .static_account_keys()
    .iter()
    .take(required)
    .position(|public_key| public_key == &signer.pubkey())
    .ok_or_else(|| io::Error::other("key is not a required transaction signer"))?;
let signature = signer.try_sign_message(&signed_transaction.message.serialize())?;
let slot = signed_transaction
    .signatures
    .get_mut(signer_index)
    .ok_or_else(|| io::Error::other("required signature slot is missing"))?;
*slot = signature;
```

</CodeGroup>

### Secp256r1 and passkeys

TypeScript runs the passkey ceremony in a WebAuthn environment. Python uses your
assertion callback. Rust signs raw P-256 authority requests with a local key;
it does not run a browser passkey ceremony.

<CodeGroup>

```typescript TypeScript
import {
  createSecp256r1PasskeySigningFn,
  signPreparedSwigTransaction,
} from '@swig-wallet/developer-sdk/signers';

const passkeySigner = createSecp256r1PasskeySigningFn({
  allowCredentials: [{ id: credentialId, type: 'public-key' }],
  userVerification: 'preferred',
});

const signed = await signPreparedSwigTransaction(prepared, {
  secp256r1: passkeySigner,
});
```

```python Python
from swig_developer_sdk import (
    create_secp256r1_passkey_signing_fn,
    sign_prepared_swig_transaction,
)

passkey_signer = create_secp256r1_passkey_signing_fn(get_webauthn_assertion)

signed = await sign_prepared_swig_transaction(
    prepared,
    secp256r1=passkey_signer,
)
```

```rust Rust
use std::sync::Arc;

use swig_developer_sdk::{Secp256r1TransactionSigner, TransactionSigner};

let signer = Secp256r1TransactionSigner::new(Arc::clone(&signing_key));
let transaction = signer.sign_prepared_transaction(prepared).await?;
```

</CodeGroup>

### Secp256k1 and EVM wallets

TypeScript/Python use an application-supplied EIP-1193 provider's `personal_sign`.
`eip1193Provider` / `eip1193_provider` is the connected wallet provider. Rust uses raw
secp256k1 authority signing, which differs from the EIP-191 format used by a
[participant signer](/developer-sdk/participant-sets#collect-member-approvals).

<CodeGroup>

```typescript TypeScript
import {
  createSecp256k1EvmSigningFn,
  signPreparedSwigTransaction,
} from '@swig-wallet/developer-sdk/signers';

const evmSigner = createSecp256k1EvmSigningFn({
  provider: eip1193Provider,
  address: evmAddress,
});

const signed = await signPreparedSwigTransaction(prepared, {
  secp256k1: evmSigner,
});
```

```python Python
from swig_developer_sdk import (
    create_secp256k1_evm_signing_fn,
    sign_prepared_swig_transaction,
)

evm_signer = create_secp256k1_evm_signing_fn(
    provider=eip1193_provider,
    address=evm_address,
)

signed = await sign_prepared_swig_transaction(
    prepared,
    secp256k1=evm_signer,
)
```

```rust Rust
use std::sync::Arc;

use swig_developer_sdk::{Secp256k1TransactionSigner, TransactionSigner};

let signer = Secp256k1TransactionSigner::new(Arc::clone(&signing_key));
let transaction = signer.sign_prepared_transaction(prepared).await?;
```

</CodeGroup>

Return the signed transaction through an authenticated application route, then
submit through your RPC provider or [Paymaster](/developer-sdk/sponsor-and-submit).
Track confirmation separately. Keep the API key, private keys, and credential
material inside their owning trust boundaries.


### Sign an ordered preparation plan

Resolve the embedded requests in every transaction using the same registered signer callbacks. The helper preserves order and stops on failure.

<CodeGroup>

```typescript TypeScript
import { signPreparedSwigTransactions } from '@swig-wallet/developer-sdk/signers';

const signedPlan = await signPreparedSwigTransactions(created.transactions, {
  secp256r1: passkeySigner,
});
```

```python Python
from swig_developer_sdk import sign_prepared_swig_transactions

signed_plan = await sign_prepared_swig_transactions(
    created.transactions, secp256r1=passkey_signer,
)
```

</CodeGroup>

Complete each transaction’s required native Solana signatures after embedded signing, then submit in the original order. These helpers do not submit or confirm the plan.

## Flow

```text
Prepared transaction
  ├─ Embedded signatures
  └─ Solana signatures
      └─ Submit
          └─ Confirm
```

Complete only the steps requested by the preparation. Changing instruction data
after outer Solana signing invalidates those signatures.

## Input

| Parameter | Description |
| :--- | :--- |
| Prepared transaction | Original result from wallet preparation, including signature requests and any participant approval plan |
| Signer | Must match the requester authority and public key used during preparation |
| Application approval | Validate the wallet, operation, recipient, amount, and expiry before asking for a signature |
| Fee-payer signature | Add after the message is final; a paymaster can supply its own signature during sponsorship |

An empty `signatureRequests` / `signature_requests` list does **not** mean the
transaction is fully signed. Embedded secp256k1/secp256r1 requests are separate
from native Ed25519 requirements in the serialized transaction.

Rust's `TransactionSigner` consumes a `PreparedTransaction` and returns a
`VersionedTransaction`. All embedded requests must match that signer.

## Errors

| Error | Meaning |
| :--- | :--- |
| Authority or public-key mismatch | The signer does not match an embedded request. Select the signer matching the original preparation. |
| Pending participant approvals | Rust native transaction signing receives an uncompiled approval plan. Collect and compile participant approvals first. |
| Outer signatures already present | Embedded data still needs patching, which changes the signed message. Resolve embedded signatures first, then collect outer Solana signatures. |
| Missing native signature | An empty embedded-request list was mistaken for a fully signed transaction. Inspect the serialized required signer set and fill each required slot. |
