## Introduction

Guardian recovery lets a designated authority replace a lost signer's key while
preserving the wallet and the protected role's permissions. Use it for an
independent backup path, configured while an authorized administrator is still
available. Creating a new passkey alone cannot recover an unconfigured wallet.

The protocol permission is `ReplaceAuthority { role_id }`, used with
`ReplaceAuthorityV1`. It preserves the target role's ID, authority type, and
actions. A passkey role therefore receives another P-256 key. Older names were
`RecoveryAuthority` and `RecoverAuthorityV1`.

## Flow

```text
+----------------------------+
| Administrator grants       |
| recovery                   |
+----------------------------+
              |
              v
+----------------------------+
| User creates a replacement |
| key                        |
+----------------------------+
              |
              v
+----------------------------+
| Guardian approves exact    |
| key                        |
+----------------------------+
              |
              v
+----------------------------+
| Replace the protected role |
| key                        |
+----------------------------+
              |
              v
+----------------------------+
| Confirm unchanged          |
| permissions                |
+----------------------------+
```

## Input

| Step | Input | Requirement |
| :--- | :--- | :--- |
| Configure | Target role ID | The one role the guardian may recover |
| Configure | Guardian public authority | Independently available key, held by a backup device, person, or service |
| Configure | Administrator | Existing authority with `All` or `ManageAuthority` grants the scoped permission |
| Replace | New public key | Same authority type as the protected role |
| Replace | Guardian authorization | Bind approval to the wallet, target role, and exact replacement key |

The guardian's role needs only `ReplaceAuthority` for the protected role. It does
not need the lost key or broad management access to perform replacement. It can
choose the key that inherits the role's power, so protect it accordingly.
A delay or cancellation mechanism requires a separate recovery policy.

## Errors

| Failure | Cause | What to do |
| :--- | :--- | :--- |
| No surviving recovery path | No authorized signer can configure or exercise the required delegation. | Configure scoped recovery while an administrator is available; a new key alone cannot restore access. |
| Replacement not authorized | The guardian lacks ReplaceAuthority for the exact target role. | Use the previously configured recovery role for that wallet and role ID. |
| Hosted preparation unavailable | The Developer SDK has no working scoped-replacement method. | Use a compatible protocol integration; compatibility types are not a recovery flow. |

## SDK example

The Developer SDK does not currently expose scoped replacement permission or a
working recovery preparation method. Compatibility recovery types do not supply
that flow. Use a compatible [Protocol SDK integration](/protocol/recovery-model)
with the [scoped permission definition](https://github.com/anagrambuild/swig-wallet/blob/3e0411f0c2980b26296903eaa4aa0c2d07869316/state/src/action/replace_authority.rs).

After confirmation, verify that the target role uses the new key and retains its
permissions. Replacing a session authority also clears its session key and expiry.

For multiple guardians, one participant-controlled recovery role would hold the
scoped permission. Giving each guardian a separate recovery role permits each
to recover independently. Connecting threshold approval to the replacement-specific
proof requires additional integration; ordinary [Participant set](/developer-sdk/participant-sets)
approval is not that proof. Hosted participant recovery is not currently supported.
