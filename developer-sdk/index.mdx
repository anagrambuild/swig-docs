The Swig Developer SDK is the current hosted wallet SDK in
`swig-ts/packages/developer-sdk`.

It is built around one idea: your server keeps the API key and prepares wallet
operations, while your client only signs the prepared transactions it is
responsible for.

## What you can build

With this SDK, you can:

- create wallets from a backend route
- prepare SOL transfers, token transfers, and Jupiter swaps
- batch multiple operations into one prepared plan
- run custom instruction execution against an existing wallet
- add guardian-based recovery flows
- submit signed transactions through Swig's sponsor path
- expose all of that through Next.js, NestJS, or your own backend routes

## Use this SDK when

- your backend should keep the Swig API key
- your client should only sign prepared transactions
- you want hosted wallet creation, movement, recovery, or sponsored submission
- you want framework route helpers instead of wiring each endpoint by hand

## Product model

1. your server creates `SwigClient` with an API key
2. your server prepares a wallet operation
3. your app returns prepared transactions and signature metadata to the client
4. the client signs only the transactions that require client authority
5. your app sends directly or calls `swig.transactions.sponsor(...)`

## Package entrypoints

The main entrypoints are:

- `@swig-wallet/developer-sdk/server/typescript` for server-side TypeScript control
- `@swig-wallet/developer-sdk/client` for client signing helpers
- `@swig-wallet/developer-sdk/browser` for browser-side wallet handles that call your proxy
- `@swig-wallet/developer-sdk/next` for Next.js route helpers
- `@swig-wallet/developer-sdk/nest` for NestJS route helpers

## Core capabilities

The current SDK exposes:

- `swig.wallets.create(...)` to prepare wallet creation
- `swig.wallets.use(...)` or `fromIdpSession(...)` to attach to a wallet
- `wallet.prepare(...)` for grouped operations
- `wallet.transfer.sol(...)` and `wallet.transfer.token(...)`
- `wallet.swap.jupiter(...)`
- `wallet.execute(...)` for custom instruction execution
- `wallet.recovery.prepareSetup(...)`, `start(...)`, `cancel(...)`, and `execute(...)`
- `swig.transactions.sponsor(...)` for paymaster-backed submission

## What it is not

- It is not the direct protocol SDK. Use `@swig-wallet/classic`,
  `@swig-wallet/kit`, or `swig-sdk` when you want direct protocol integration.
- It is not a browser-direct API client. The API key belongs on the server.
- It is not the richer legacy policy-helper client in `@swig-wallet/developer`.
- It does not currently ship a dedicated `secp256k1` client signing helper the
  way it does for passkeys.
