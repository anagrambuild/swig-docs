Every wallet read is an API-key `GET`. Reads follow the client's retry policy,
so they are safe to repeat.

## Start from a wallet handle

<CodeGroup>

```typescript TypeScript
const wallet = swig.wallets.use({
  swigConfigAddress,
  walletAddress,
});
```

```python Python
wallet = swig.wallets.use(swig_config_address)
```

</CodeGroup>

Reads do not need a `requesterAuthority` / `requester_authority`. Only
preparation calls do.

In Rust, use the `wallet` client from
[Choose a Language](/developer-sdk/integration-paths#rust).

## Balances

<CodeGroup>

```typescript TypeScript
const usd = await wallet.getUsdBalance();
// usd.swigConfigAddress, usd.walletAddress, usd.usdValue

const tokens = await wallet.listTokenBalances();
for (const balance of tokens.balances) {
  console.log(
    balance.assetKind,
    balance.tokenSymbol,
    balance.uiAmount,
  );
}
console.log(tokens.totalUsdValue);
```

```python Python
usd = await wallet.get_usd_balance()
# usd.swig_config_address, usd.wallet_address, usd.usd_value

tokens = await wallet.list_token_balances()
for balance in tokens.balances:
    print(balance.asset_kind, balance.token_symbol, balance.ui_amount)
print(tokens.total_usd_value)
```

```rust Rust
let usd = wallet.get_usd_balance(&swig_config_address).await?;

let balances = wallet.list_token_balances(&swig_config_address).await?;
if let Some(sol) = &balances.sol_balance {
    println!("SOL lamports: {}", sol.lamports);
}
for (mint, token) in &balances.token_balances {
    println!("{mint}: {} {} base units", token.amount_raw, token.symbol);
}
```

</CodeGroup>

In TypeScript and Python, each balance carries `mintAddress` / `mint_address`, `tokenProgram` /
`token_program`, `tokenSymbol`, `tokenName`, `decimals`, `amountRaw` /
`amount_raw`, `uiAmount` / `ui_amount`, `usdPrice` / `usd_price`, and
`usdValue` / `usd_value`, and `assetKind` / `asset_kind`. The SDK normalizes
the asset discriminator to `token`, `native-sol`, or `unspecified`.

In TypeScript and Python, use `amountRaw` / `amount_raw` for arithmetic. It is
the exact integer amount as a string; `uiAmount` / `ui_amount` is a display
convenience.

In Rust, `sol_balance` holds native SOL and `token_balances` is keyed by mint.
Use `lamports` and `amount_raw` (`u64`) for arithmetic. `ui_amount` and USD
values (`f64`) are for display.

## Token activity

<CodeGroup>

```typescript TypeScript
const activity = await wallet.listTokenTransactions({ limit: 25 });

for (const transaction of activity.transactions) {
  console.log(
    transaction.transactionSignature,
    transaction.direction, // 'inflow' | 'outflow'
    transaction.assetKind, // 'token' | 'native-sol' | 'unspecified'
    transaction.uiAmount,
    transaction.tokenSymbol,
  );
}
```

```python Python
activity = await wallet.list_token_transactions(limit=25)

for transaction in activity.transactions:
    print(
        transaction.transaction_signature,
        transaction.direction,  # "inflow" | "outflow"
        transaction.asset_kind,
        transaction.ui_amount,
        transaction.token_symbol,
    )
```

```rust Rust
use swig_developer_sdk::{AssetTransfer, ListSwigTokenTransactionsArgs};

let activity = wallet
    .list_token_transactions(ListSwigTokenTransactionsArgs {
        swig_config_address,
        limit: Some(25),
    })
    .await?;

for transaction in &activity.transactions {
    match &transaction.transfer {
        AssetTransfer::Sol { lamports, .. } => println!("SOL: {lamports}"),
        AssetTransfer::Token { mint_address, amount_raw, .. } => {
            println!("{mint_address}: {amount_raw}");
        }
    }
}
```

</CodeGroup>

Each entry carries `slot`, optional `blockTime` / `block_time`,
`ownerAddress` / `owner_address`, and `isSubaccount` / `is_subaccount`.
TypeScript and Python include `tokenAccountAddress` / `token_account_address`
and the balance amount, USD, and normalized asset-kind fields directly on the
entry. Rust groups asset-specific fields under `transfer` (`AssetTransfer`).

`limit` is optional. Omit it for the backend default of 25. Values above 100
are capped at 100.

Rust reports direction as `TransactionDirection::{Inflow, Outflow}`.

## Roles

Roles are how you inspect who currently holds authority over a Swig and what
each authority is allowed to do.

<CodeGroup>

```typescript TypeScript
const { swigConfigAddress, walletAddress, roles } = await wallet.listRoles();

for (const role of roles) {
  console.log(role.roleId, role.authorityType, role.authorityValue);

  for (const action of role.actions) {
    console.log(action.actionIndex, action.actionCode, action.actionData);
  }
}
```

```python Python
result = await wallet.list_roles()

for role in result.roles:
    print(role.role_id, role.authority_type, role.authority_value)

    for action in role.actions:
        print(action.action_index, action.action_code, action.action_data)
```

```rust Rust
use swig_developer_sdk::SwigRolePermission;

let result = wallet.list_roles(&swig_config_address).await?;
for role in &result.roles {
    for action in &role.actions {
        if let SwigRolePermission::SolLimit { amount } = &action.permission {
            println!("Role {} has {amount} lamports remaining", role.role_id);
        }
    }
}
```

</CodeGroup>

TypeScript and Python expose these role fields:

| Field | Meaning |
| :--- | :--- |
| `roleId` / `role_id` | the role's on-chain index |
| `authorityType` / `authority_type` | protocol authority type discriminant |
| `authorityValue` / `authority_value` | the authority's public key material |
| `actions` | the permissions attached to that role |
| `actionCode` / `action_code` | protocol action discriminant |
| `actionData` / `action_data` | raw per-action payload |

TypeScript's `actionData` and Python's `action_data` are raw objects whose shape
depends on the action.
Read it against the protocol's
[permissions model](/protocol/concepts-and-permissions) rather than assuming
fixed keys.

Rust decodes each role into `SwigRoleAuthority` and each action into
`SwigRolePermission`. Read current allowance fields from those variants.
Unsupported or malformed role data returns `ListRolesError::InvalidResponse`.

Common uses:

- confirm a newly granted authority actually landed on-chain
- render "who can spend from this wallet" in an admin view
- check whether a passkey or EVM authority is still attached before preparing
  a transaction it would need to sign

## Rent claimer

TypeScript `0.11.0` adds a finalized read of the V2 Swig's rent recipient:

```typescript
const rentClaimer = await wallet.getRentClaimer({ network: 'mainnet' });
// A public key string, or null when a valid config has no recipient.
```

The network may also come from the wallet handle or client. Errors are not
treated as an unset recipient. See [Rent Claimers](/developer-sdk/rent-claimers)
for setup and the separate setter. This read is unavailable in Python and
Rust `0.1.0`.

## DEX activity

DEX transaction history and the latest state of liquidity positions are a

## Policy metadata

Policy reads are a separate, portal-scoped lookup rather than a wallet read:

<CodeGroup>

```typescript TypeScript
const policy = await swig.wallets.getPolicy(policyId);
```

```python Python
policy = await swig.wallets.get_policy(policy_id)
```

```rust Rust
let policy = wallet.get_policy(&policy_id).await?;
```

</CodeGroup>

See [Read Policy Templates](/examples/dev-portal/fetch-policy) for policy response
fields and how to use the saved configuration.

Rust reports an unknown policy as `GetPolicyError::PolicyNotFound`.
Propagate other read errors rather than returning an empty balance or role list.

## Underlying routes

| Read | Route |
| :--- | :--- |
| USD balance | `GET /wallet/swig/{swig_config_address}/balance/usd` |
| Token balances | `GET /wallet/swig/{swig_config_address}/token-balances` |
| Token transactions | `GET /wallet/swig/{swig_config_address}/token-transactions` |
| Roles | `GET /wallet/swig/{swig_config_address}/roles` |
| Rent claimer | `GET /transaction/wallet/{swig_address}/rent-claimer?network=NETWORK_MAINNET` |
| Policy | `GET /wallet/policies/{policy_id}` |

Call these API-key routes from a trusted server. Use your application API to
return validated data that the user is authorized to see. Keep the Developer
SDK client on the server.
