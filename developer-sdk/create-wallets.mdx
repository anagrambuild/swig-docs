Prepare a new Swig wallet from a saved policy template or an inline authority. Your
application signs and submits the returned transactions to create it on-chain.

Rust uses `WalletClient::prepare_create_wallet`. The examples use `wallet` from
[Rust integration](/developer-sdk/integration-paths#rust), with `fee_payer` and
`user_public_key` supplied as `Pubkey` values.

## Two create modes

You can create a wallet either:

- from a policy template with `policyId` / `policy_id`
- from an inline `initialUser` / `initial_user`

If the policy ID is omitted, the backend creates the wallet from the inline
authority you provide. Supported authority shapes are `ed25519`, `secp256k1`,
and `secp256r1`.

In Rust, a saved policy uses `policy_id: Some(policy_id)` with a `String` ID.
`initial_user` is an `Option<WalletAuthority>`. It contains an authority when
the policy requests a key at creation, or `None` when the policy supplies one.

```rust
use swig_developer_sdk::PrepareCreateWalletArgs;

let created = wallet
    .prepare_create_wallet(PrepareCreateWalletArgs {
        fee_payer,
        policy_id: Some(policy_id),
        initial_user,
    })
    .await?;
```

## Basic create flow

<CodeGroup dropdown>

```typescript TypeScript
const created = await swig.wallets.create({
  feePayer,
  initialUser: {
    ed25519: {
      publicKey: userPublicKey,
    },
  },
});
```

```python Python
created = await swig.wallets.create(
    fee_payer=fee_payer,
    initial_user={
        "ed25519": {
            "publicKey": user_public_key,
        },
    },
)
```

```rust Rust
use swig_developer_sdk::{PrepareCreateWalletArgs, WalletAuthority};

let created = wallet
    .prepare_create_wallet(PrepareCreateWalletArgs {
        fee_payer,
        policy_id: None,
        initial_user: Some(WalletAuthority::Ed25519 {
            public_key: user_public_key,
        }),
    })
    .await?;
```

</CodeGroup>

In Rust, `passkey_public_key` and `evm_public_key` are compressed SEC1 public
keys as `[u8; 33]`. Preparation validates that the supplied key lies on the
selected curve.

## What you get back

TypeScript and Python return a categorized create plan:

| TypeScript / Python | Meaning |
|-------|---------|
| `wallet` | the config address, wallet address, and resolved network |
| `transactions` | full ordered transaction list |
| `clientAuthorityTransactions` / `client_authority_transactions` | transactions with explicit embedded `secp256r1` or `secp256k1` signature requests |
| `feePayerOnlyTransactions` / `fee_payer_only_transactions` | transactions without explicit signature requests; verify the Solana required signer set before treating them as fee-payer-only |
| `creationTransaction` / `creation_transaction` | the create transaction itself |

For a plain create, this usually collapses to one creation transaction whose
only required transaction signer is the fee payer. Policy-driven follow-up
instructions can add other signer requirements.

Rust returns `WalletCreation { wallet, transaction }`. The wallet contains
native config and wallet `Pubkey` addresses. `transaction` is one
`PreparedTransaction`, whose `transaction` field is a native
`VersionedTransaction` and whose `signature_requests` contains any requested
embedded signatures.

Rust currently requires exactly one transaction in the creation response.
A policy that produces multiple transactions returns
`PrepareCreateWalletError::InvalidResponse("expected exactly one prepared transaction")`.
Use TypeScript or Python for those policy plans. A missing inline authority
without a policy, an empty policy ID, or a ParticipantSet initial authority
returns `PrepareCreateWalletError::InvalidInput`.

## Networks

TypeScript and Python resolve the network from the call and then the client
default. Wallet creation requires one of those values to be set. Rust uses the
`Network` configured on `WalletClient` for every request.

## What to submit

For TypeScript and Python, submit the prepared `transactions` exactly in the
returned order. In Rust, sign and submit the returned `transaction`.

If the client-authority collection is not empty, your application must obtain
and patch each requested embedded signature outside the server SDK before
submission. An empty collection does not prove that the transaction needs no
application signature; inspect each serialized transaction's required signer
set as well. The field name comes from the hosted API schema; it is not a
browser SDK surface.
