A policy stores reusable wallet-creation configuration. The Developer Portal
calls these policies **Wallet templates**: each template defines an initial
wallet user and can include additional users with their own allowed actions.
Pass the policy ID when you [Create Wallets](/developer-sdk/create-wallets).

An [API key](/examples/dev-portal/create-api-key) authenticates your server's
requests. The template supplies wallet configuration; your application still
signs and submits the prepared transactions.

## Initial user and additional users

The portal's initial wallet user receives **full root access** (`All`). Choose
an authority you trust to administer the wallet. The portal form does not
provide a spending-limit editor for this initial user.

Additional wallet users have separate authorities and allowed actions. Use
[Permissions](/developer-sdk/permissions) to understand those grants. The
reference describes the Developer SDK's complete action list; the portal
provides a smaller set of controls for common configurations.

## Create a template

Open **Wallet templates** in your project in the
[Developer Portal](https://dashboard.onswig.com) and select **New template**.

<Steps>
  <Step title="Name the template and set the initial user">
    Enter a template name and an optional description. Choose how to provide
    the initial user's public key:

    - **Provided at wallet creation:** your application supplies the authority
      through `initialUser` in TypeScript or `initial_user` in Python.
    - **Set a key now:** choose the key type and save a public key in the
      template. This authority is reused for wallets created from it.

    Both choices give the initial user full root access.
  </Step>
  <Step title="Review recovery availability">
    The portal currently marks **Enable recovery guardian** as **Coming soon**
    and disables it. See [Guardian recovery](/developer-sdk/permissions#guardian-recovery)
    for scoped key replacement and the additional integration required for
    single-guardian and multiple-approval recovery.
  </Step>
  <Step title="Add other wallet users if needed">
    Additional users must have a public key set in the template. Choose each
    user's key type, public key, and allowed actions. Each additional user
    needs at least one action.

    For spending limits or program access, review the selected fields against
    [Permissions](/developer-sdk/permissions). The portal's SOL amount input
    uses SOL; the SDK's action inputs use lamports.
  </Step>
  <Step title="Review and create">
    Check the initial user's root access and each additional user's authority
    and actions, then select **Create template**. Save the resulting policy
    ID for your server integration.
  </Step>
</Steps>

## Add a role with a spending limit

For a concrete limited-transfer example, create the wallet, then follow
[Add Roles](/developer-sdk/add-roles-and-permissions#add-a-scoped-sol-transfer-role).
That example gives a separate authority access to the System Program and a
total allowance of 1,000,000 lamports. It grants only `program` and `solLimit`
to the new role; the wallet's initial root authority keeps its existing power.

After submitting the add-role transaction, read the wallet's roles to verify
that the new authority has the intended actions. A template's stored metadata
and a wallet's confirmed on-chain roles are separate records.

## Read and use a policy

Use [Read Policies](/examples/dev-portal/fetch-policy) to inspect saved policy
metadata. Use [Create Wallets](/developer-sdk/create-wallets) to prepare a wallet
from the policy ID, then sign and submit its transactions.

To change access on an existing wallet, use the wallet's authority-management
operations, such as [Add Roles](/developer-sdk/add-roles-and-permissions).
Editing or deleting a saved template does not rewrite roles already on-chain.
