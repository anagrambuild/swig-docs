## Introduction

- **Use when:** you need to limit what a wallet role can do.
- **For:** applications assigning access to owners, operators, guardians, or session keys.

## How it works

1. Choose the authority that will use the role.
2. Build its permissions with `Actions.set()` and finish with `.get()`.
3. Add the role with that authority and permission set.
4. Use the role ID when authorizing transactions. Its permissions apply to each operation.

## Permission groups

- [Spending limits](/solana/permissions/spending-limits): SOL, token, and staking budgets, with recurring and destination restrictions.
- [Program access](/solana/permissions/program-access): allowed programs and program scopes.
- [Administrative](/solana/permissions/administrative): role management, key replacement, wallet closure, authorization locks, and subaccounts.

## Example: a SOL transfer role

```typescript
import { SystemProgram } from "@solana/web3.js";
import { Actions } from "@swig-wallet/classic";

const actions = Actions.set()
  .programLimit({ programId: SystemProgram.programId })
  .solLimit({ amount: 100_000_000n })
  .get();
```

- `Program` allows calls to the System Program.
- `SolLimit` allows a total spend of 0.1 SOL; successful spends reduce the remaining budget.
- Both are required for this scoped transfer role.

Pass `actions` to [add a role](/solana/add-role).

## Keep delegation scoped

- Give application roles the programs and asset budgets they need.
- Keep `manageAuthority()` on trusted administrators: it allows them to grant access to others.
- A role needs `manageAuthorizationLocks()` explicitly to place holds, including an `all()` role.
- A session uses its role's existing permissions; a shorter session does not reduce its spending budget.

See [Transfers](/solana/use-cases/transfers),
[Authorization locks](/solana/use-cases/authorization-locks), and
[Recovery](/solana/use-cases/recovery) for complete flows.
